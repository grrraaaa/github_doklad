## Слайд 1. Титул — «Git, деплой и ИИ-агенты» (~1 мин)

**На слайде:** заголовок + «Как не лежать в простое • 7 тем за 20 минут».

**Говорить:**
> Всем привет! Я расскажу, как код из головы разработчика попадает в прод и не ломает всё по дороге. Разберём Git, GitHub и GitLab, ветки, деплой фич, пул-реквесты, ревью и конфликты. И отдельно — что в этом всём уже умеют ИИ-агенты, а где человек всё ещё обязателен.
>
> Название не случайно: главный враг — **вынужденный простой**, когда команда сидит и ждёт, пока кто-то починит сломанный main. Сегодня покажу, как ветки и правильные ворота в прод превращают «все стоят, теряем 500» в «быстро чиним и зарабатываем 200». Что за 200 и 500 — расскажу на слайде 8, это условные деньги, но логика настоящая.

**Переход:** «Сначала — карта доклада».

**Могут спросить:** «Это про GitHub или GitLab?» — Ответ: про оба, команды Git одинаковые, разница только в кнопках (слайд 4).

Потом практика: жизненный цикл фичи, окружения, PR, ревью, конфликты. В конце — 5 правил на одном слайде, сфотографируете, и живое демо: создам ветку, открою PR и волью его за 3 минуты.

## Слайд 3. Git = снапшоты, а не файлы (~2 мин)

**На слайде:** три плашки commit / branch / merge + место под скриншот `git log --graph`.

**Говорить:**
> Главная mental-модель: **Git хранит не файлы, а снапшоты** — слепки всего проекта в момент времени. Каждое сохранение — **commit**: уникальный id, автор, сообщение, ссылка на родителя.
>
> **Branch** — просто подвижный указатель на коммит. Создать ветку — это секунда, потому что файлы не копируются. **Merge** — склейка двух линий истории.
>
> Всё это работает **локально**: коммитить, ветвить и откатывать можно в самолёте. Сервер (GitHub/GitLab) нужен для синхронизации и страховки: `push` — отдать, `pull` — забрать.
>
> Покажите скриншот (Ш1): вот так выглядит история — точки-коммиты и разветвления. Читать её должен уметь каждый.

**Ключевые команды (произнести):** `git init, git add, git commit -m, git branch, git switch, git merge, git log --graph --oneline`.

**Переход:** «Где живут удалённые репозитории — GitHub и GitLab».

**Могут спросить:** «Чем commit отличается от сохранения в Word?» — Ответ: коммит — слепок всего проекта с историей и автором, к нему можно вернуться в любой момент.

## Слайд 4. GitHub vs GitLab (~2 мин)

**На слайде:** две колонки + место под скриншот двух страниц репозитория.

**Говорить:**
> Путаница частая, запомните одним предложением: **Git — инструмент, GitHub и GitLab — сайты-хостинги для Git-репозиториев**, как почта и почтовый клиент.
>
> **GitHub** — самый популярный, стандарт де-факто: pull requests, Actions для CI/CD, Codespaces, огромное open-source сообщество. Если идёте в open source — вам сюда.
>
> **GitLab** — «всё в одном»: merge requests (то же, что PR, другое название), встроенный CI/CD из коробки, удобно ставить на свой сервер компании. Многие enterprise-команды сидят на нём.
>
> Для нашего доклада разницы почти нет: ветки, PR/MR, ревью и конфликты везде одинаковые, отличаются только названия кнопок. Покажите скриншот (Ш2): один и тот же проект в двух интерфейсах.

**Переход:** «А теперь модная тема — ИИ-агенты».

## Слайд 5. ИИ-агенты деплоят сами? (~2 мин)

**На слайде:** 4 плашки Код / Тест / Деплой / Откат + скриншот лога агента.

**Говорить:**
> **ИИ-агент — это не чат, а цикл: план → действие → проверка.** Ему дают задачу (issue), доступ к репозиторию и терминалу, и он крутится: читает код, правит, запускает тесты, смотрит результат, чинит.
>
> Что он уже реально умеет в сфере деплоя — четыре вещи на слайде: **написать фичу** по issue, **прогнать тесты**, **выкатить на stage-окружение** и даже **откатить**, если метрики упали.
>
> Чего он НЕ умеет: **нести ответственность**. Поэтому правило простое, оно будет и в финале: **агент готовит — человек отвечает**. Агент может открыть PR и даже задеплоить на тестовый стенд, но кнопку «в прод» жмёт человек после ревью. Покажите лог (Ш3): агент сам создал ветку, открыл PR, CI зелёный — дальше ход человека.

**Могут спросить:** «Агент заменит деплой-инженера?» — Ответ: рутину (шаблонные PR, чинка упавших тестов, раскатка на stage) — да, сократит. Решение о проде и разбор аварий — нет.

**Переход:** «Разберём этот цикл по шагам».

## Слайд 6. Агент: план → код → прод (~1,5 мин)

**На слайде:** цепочка из 4 шагов со стрелками + фраза «человек жмёт кнопку в прод».

**Говорить:**
> Цепочка такая. **Шаг 1 — план:** агент читает issue и составляет план изменений. **Шаг 2 — код:** создаёт ветку и правит файлы — заметьте, тоже в ветке, как человек! **Шаг 3 — проверка:** запускает тесты и ждёт ревью. **Шаг 4 — деплой:** максимум — автоматический выкаты на stage.
>
> А дальше — **ворота**: прод только руками. Это осознанное ограничение, а не баг. Даже если агент уверен на 99%, последний процент — ваша репутация и деньги компании.
>
> Если останется время в конце — покажу живьём, как агент чинит упавший тест. Это самый честный пример пользы.

**Переход:** «Возвращаемся к базе: как вообще устроены ветки».

## Слайд 7. main — священен (~2 мин)

**На слайде:** main / feature/* / hotfix/* + скриншот графа веток.

**Говорить:**
> **Анатомия ветвления за 30 секунд.** Есть одна святая ветка — **main**: она всегда собирается и всегда работает. Напрямую в неё никто не коммитит — это табу.
>
> Вся работа — в коротких ветках: **feature/название** — новая фича, живёт день-два и вливается обратно. **hotfix/название** — срочный фикс прода, ответвляется от main и вливается обратно максимально быстро.
>
> Покажите граф (Ш4): main — прямая линия, от неё отходят веточки и возвращаются. Правило чтения: ветка началась от свежего main и быстро вернулась — человек молодец. Ветка живёт неделю и разрослась — будет боль при merge.
>
> Две команды, которые должны отскакивать от зубов: `git switch -c feature/поиск` — создать и перейти, `git switch main` — вернуться.

**Переход:** «А теперь обещанная экономика — про 200 и 500».

## Слайд 8. 200 заработать, 500 потерять (~2 мин, фишка доклада)

**На слайде:** две большие цифры −500 / +200.

**Говорить (рассказать как историю):**
> Объясняю заголовок. Цифры **условные**, это мнемоника, а не бухгалтерия — так и скажите, если спросят.
>
> Представьте: кто-то запушил в main напрямую, прод лёг. Вся команда из пяти человек сидит час и ждёт — это **вынужденный простой**. Назовём убыток **минус 500**: зарплата капает, клиенты уходят, ничего не производится.
>
> А теперь правильный сценарий: прод чинят не паникой в main, а короткой **hotfix-веткой**: фикс → тесты → PR → merge → деплой за 20 минут. Сервис встал быстро, остаток часа команда снова пилит фичи. Относительно часового простоя мы **«заработали» плюс 200** — сэкономили большую часть потерь и сохранили репутацию.
>
> **Мораль одной фразой: вынужденный простой дороже быстрой победы. Чини веткой, а не паникой.** Именно поэтому main свят, а hotfix — короткий.

**Переход:** «Чтобы так получалось всегда, у фичи есть конвейер».

## Слайд 9. Путь фичи: идея → прод (~2 мин)

**На слайде:** цепочка из 6 шагов + скриншот доски Issues.

**Говорить:**
> **Жизненный цикл фичи — 6 шагов, ни один не пропускаем.** **Идея** — заводим issue: что делаем и зачем, без этого работа невидима. **Ветка** — `feature/...` от свежего main. **Код** — маленькие коммиты с понятными сообщениями. **PR** — открываем ворота в main и зовём ревью. **Stage** — смотрим фичу на окружении-копии прода. **Прод** — merge и деплой.
>
> Важно: **каждый шаг оставляет след** в GitHub/GitLab: issue, ветка, коммиты, обсуждение в PR, зелёные галочки CI. Если фича сделана «мимо» — её нельзя проверить, откатить и вспомнить через месяц, кто и зачем это писал.
>
> Покажите доску (Ш5): issue едет по колонкам To Do → In Progress → Done — это тот же путь, вид сверху.

**Переход:** «Шаг “stage” заслуживает отдельных слов — про окружения».

## Слайд 10. dev → stage → prod (~1,5 мин)

**На слайде:** три окружения + скриншот pipeline.

**Говорить:**
> **Три окружения — три степени страха.** **dev** — песочница разработчика, ломать можно и нужно. **stage** — копия прода: те же данные (обезличенные), те же настройки; сюда выкатываем кандидата на релиз и кликаем руками. **prod** — боевые пользователи, трогаем только проверенное и только через PR.
>
> Деплой идёт **лесенкой**: dev → stage → prod, и каждая ступень — с автоматическими проверками. Покажите pipeline (Ш6): зелёные галочки по трём стадиям. Красный крест на stage — в прод не едем, чиним в ветке.
>
> ИИ-агенту можно разрешить деплоить на dev хоть каждый коммит, на stage — после тестов, на prod — никогда самому.

**Переход:** «А кто стоит на воротах в main? Pull Request».

## Слайд 11. Pull Request = ворота в main (~2 мин)

**На слайде:** 4 шага + скриншот страницы PR.

**Говорить:**
> **Pull Request — это просьба: «посмотрите мою ветку и влейте её в main».** Это не просто кнопка, а место, где встречаются код, тесты и люди.
>
> Анатомия хорошего PR — 4 шага на слайде: **создай** (запушил ветку, написал что и зачем, приложил скрин), **проверки** (CI прогнал тесты — ждём зелёный), **обсуди** (ревью, правки), **влей** (merge, ветку удаляем).
>
> Покажите страницу PR (Ш7): сверху описание, посередине diff — что изменилось, сбоку галочки Checks, внизу кнопка Merge, которая активируется только после ревью и зелёного CI. **Правило: маленький PR на 100–200 строк вливается за день, простыня на 2000 строк висит неделю.** Дробите работу.

**Переход:** «Внутри PR живёт самая человеческая часть — ревью».

---

## Слайд 12. Review: найди баг до прода (~2 мин)

**На слайде:** чек-лист из 4 пунктов + скриншот комментария + фраза про 15 минут.

**Говорить:**
> **Code review — это поиск бага, когда он стоит копейки, а не когда он уже в проде.** Смотреть надо четыре вещи: **логика и крайние случаи** (а что если пусто? а если ноль? а если нет сети?), **тесты и читаемость** (поймёт ли код новичок через полгода?), **безопасность** (нет ли паролей и токенов в коде — самая частая боль!), **тон** (комментируем код, а не человека).
>
> Покажите скриншот (Ш8): ревьюер не ругается, а предлагает — кнопка Suggest, автор принимает в один клик, потом Approve. Идеальный диалог: «а давай так?» — «давай».
>
> И золотое правило снизу слайда: **маленький PR ревьювят за 15 минут, большой — никогда.** Хотите быстрое ревью — делайте маленькие PR. Хотите быть хорошим ревьюером — отвечайте в тот же день.

**Переход:** «А что бывает, когда две хорошие ветки встретились — конфликты».

## Слайд 13. Конфликт: два правят одно (~2 мин)

**На слайде:** 3 шага pull / resolve / push + скриншот маркеров.

**Говорить:**
> **Merge-конфликт — не ошибка и не позор. Это встреча двух правок в одном месте:** вы и коллега поменяли одни и те же строки по-разному, Git честно говорит «решите сами, я не знаю, чья правда».
>
> Лечится тремя шагами: **pull** — забираем чужое, **resolve** — открываем файл, видим маркеры `<<<<<<< HEAD ... ======= ... >>>>>>>`, оставляем правильный вариант (часто — комбинацию обоих), **push** — отправляем мир обратно.
>
> Покажите маркеры (Ш9) — их вид надо узнать один раз и перестать бояться. Два правила профилактики: **частый pull** из main в свою ветку (конфликты маленькие и свежие) и **поговорить с автором** второй правки перед тем, как кликать. Руками удалять чужой код молча — запрещено.

**Могут спросить:** «А если уже всё сломал при резолве?» — Ответ: `git merge --abort` — отмена слияния, и начать заново, ничего не потеряно.

**Переход:** «Собираем всё в пять правил».

**На слайде:** пять правил — попросить сфотографировать.

> **Первое:** main не ломаем, работаем в ветках. **Второе:** маленький PR лучше большого подвига. **Третье:** зелёный CI плюс ревью равно merge — без исключений. **Четвёртое:** конфликт? Сначала говорим с человеком, потом кликаем. **Пятое:** агент готовит, человек отвечает — кнопку в прод жмёт тот, кто готов чинить ночью.

**Переход:** «Вопросы — и покажу всё живьём».

## Слайд 15. Спасибо! Вопросы? + демо (~3 мин)

**На слайде:** «Демо: ветка → PR → merge за 3 минуты» + строка для ника и имени (замени!) .

**Говорить:**
> Спасибо! Теперь вопросы — и покажу полный цикл живьём за 3 минуты.

**Сценарий демо (отрепетируй заранее!):**
1. `git switch -c feature/demo` — создал ветку.
2. Меняю одну строку (заранее подготовь файл), `git add .`, `git commit -m "demo: add greeting"`, `git push -u origin feature/demo`.
3. В браузере: Compare & pull request → короткое описание → Create.
4. Показать: diff, Checks (если CI настроен — зелёный), сам себе оставляю комментарий-ревью и жму Approve/Merge. Ветку удаляю.
5. `git switch main`, `git pull`, `git log --oneline -5` — показать, что коммит приехал.
6. Финальная фраза: «Этот путь — issue → ветка → PR → review → merge — вы теперь видели целиком. Заведите сегодня свой репозиторий и повторите».

**Если демо упадёт (нет интернета/CI):** не паниковать, сказать «прод Jenkins тоже так говорит» и показать те же шаги на заранее снятых скриншотах Ш7–Ш8. Подготовь их как план Б.

**Типичные вопросы и короткие ответы:**
- *GitHub или GitLab выбрать для пет-проекта?* — GitHub: больше примеров и open source.
- *Нужен ли Git одному?* — Да: история, откаты, бэкап, портфолио.
- *Агент сам вольёт в прод?* — Только если вы ему разрешите. Не разрешайте.
- *Что за 200 и 500, это реальные деньги?* — Нет, условные единицы для запоминания: простой стоит дорого, быстрый фикс окупается.
- *С чего начать сегодня?* — Создать репозиторий, запушить, открыть первый PR самому себе.

---

**Удачи! Говори спокойно, кликай медленно, на вопросы «не знаю» отвечай честно: «хороший вопрос, проверю и напишу».**
