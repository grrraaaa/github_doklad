# Скриншоты для презентации — какие сделать, как и куда вставить

**Презентация:** `Git_deploy_prezentatsiya.pptx`. На слайдах есть серые плашки «СКРИНШОТ N» — это заглушки. Замени каждую плашку скриншотом (клик по плашке → Delete, затем Вставка → Рисунки → вставить свой PNG).

Всего нужно **9 скриншотов (Ш1–Ш9)**. Без них доклад работает (схемы уже нарисованы), но со скриншотами — в разы убедительнее. По времени: ~1 час на всё, если делать по инструкции ниже.

---

## Общие требования ко всем скриншотам

- **Размер:** окно 16:9, итоговый PNG ~1920×1080 или обрезанный фрагмент 1600×900. В PowerPoint тяни за уголок, не растягивай.
- **Чистота:** закрой лишние вкладки, выйди из личных чатов. Ник/аватар можно оставить — это твой проект.
- **Шрифт:** в терминале увеличь шрифт (Ctrl + `+`), чтобы было видно с последнего ряда.
- **Язык интерфейса:** английский (так привычнее залу), но русский тоже ок — главное одинаково везде.
- **Что скрыть:** токены, пароли, email — замажь прямоугольником в Paint перед вставкой.
- **Где хранить:** сложи все PNG в папку `screenshots/` рядом с презентацией, называй `sh1_gitlog.png`, `sh2_github_gitlab.png` и т.д.

### Быстрый демо-репозиторий для всех скриншотов (сделай один раз)

```bash
git init demo-deploy
cd demo-deploy
git config user.name "Твоё Имя"
git checkout -b main
echo "# demo-deploy" > README.md
git add . && git commit -m "init: readme"
git checkout -b feature/search
echo "search v1" > search.txt
git add . && git commit -m "feat: add search v1"
git checkout -b feature/pay
echo "pay v1" > pay.txt
git add . && git commit -m "feat: add pay v1"
git checkout main
git merge feature/search --no-ff -m "merge search"
```

Залей на GitHub (и при желании такой же на GitLab) — получишь материал для Ш2, Ш4, Ш5–Ш8.

## Ш1. `git log --graph` → слайд 3

**Что должно быть видно:** цветной граф: 2–3 ветки, 5–8 коммитов, подписи `* main`, `feature/...`.
**Как сделать:**
1. В папке `demo-deploy` создай ещё пару веток/коммитов (см. команды выше).
2. В терминале выполни:
```bash
git log --graph --oneline --all -12 --decorate
```
3. Увеличь шрифт, растяни окно шире, сделай скриншот только окна терминала (Win+Shift+S).
4. Обрежь так, чтобы не было пустого места.

**Критерий готовности:** с 3 метров видно разветвление.
**План Б:** если графа нет — сними вывод любых 5 коммитов, ветвление дорисуй словами.

## Ш2. GitHub + GitLab рядом → слайд 4

**Что должно быть видно:** два окна браузера рядом: слева репозиторий в GitHub, справа тот же в GitLab (название, файлы, кнопка истории).
**Как сделать:**
1. Залей `demo-deploy` на GitHub (инструкция GitHub: Create repository → push).
2. Создай пустой проект в GitLab и запушь туда же:
```bash
git remote add gitlab <url-gitlab-проекта>
git push gitlab main
```
3. Поставь окна рядом (Win + стрелка влево/вправо), масштаб страницы 110–125%.
4. Один скриншот обоих окон.

**Критерий:** видны логотипы/адреса github.com и gitlab.com + одинаковые файлы.
**План Б:** два отдельных скриншота друг под другом или вообще пропустить — на слайде уже есть сравнение текстом.

## Ш3. Лог ИИ-агента → слайд 5

**Что должно быть видно:** что агент сам сделал: список шагов (прочитал issue → создал ветку → открыл PR) + ссылка на PR / зелёный CI. Это самый «вау»-скриншот.
**Варианты (выбери любой один):**
- **A. Copilot Workspace / Chat:** попроси «создай ветку feature/agent-fix и исправь опечатку в README», сними ответ со списком действий + созданный PR.
- **B. Любой агент в терминале (Aider, Copilot CLI):** запусти, сними лог с `git diff` и `pytest passed`.
- **C. Честный минимум:** скриншот Actions-запуска, где видно «AI-fix: tests passed», + подпись голосом «агент починил тест и открыл PR».

**Как оформить:** обрежь до 3–5 ключевых строк, подчеркни красным (Вставка → Фигуры → Прямоугольник без заливки) строку «opened pull request».
**План Б:** пропустить — на слайде уже есть 4 плашки способностей, скажи «агента покажу живьём в конце».

## Ш4. Граф веток → слайд 7

**Что должно быть видно:** main + ответвления feature + hotfix и их возврат (слияния).
**Как сделать (2 варианта, хватит одного):**
- **Терминал:** та же команда, что в Ш1, но с подписями веток:
```bash
git branch hotfix/crash
git log --graph --oneline --all --decorate -15
```
- **GitHub:** вкладка Insights → Network — красивые цветные линии. Сними её.

**Критерий:** видно, что ветки начинаются от main и вливаются обратно.
**Куда вставить:** вместо серой плашки на всю ширину слайда.

## Ш5. Доска Issues → слайд 9

**Что должно быть видно:** 3 колонки To Do / In Progress / Done, 3–5 карточек («поиск», «оплата», «фикс краша»), одна карточка в Done с галочкой.
**Как сделать:**
1. GitHub → Issues → New issue: создай 3 задачи («Добавить поиск», «Экран оплаты», «Падение при пустой строке»).
2. Projects → New project (Board) → перетащи: одну в Done (закрой issue), одну в In Progress, одну в To Do.
3. Сними всю доску.

**Критерий:** читаются названия колонок и хотя бы 3 карточки.
**План Б:** сними просто список Issues с одной закрытой (фиолетовая галочка Closed) — смысл тот же.

## Ш6. Pipeline dev → stage → prod → слайд 10

**Что должно быть видно:** три стадии с зелёными галочками. Самый простой путь — GitHub Actions с минимальным workflow.
**Как сделать (15 мин):**
1. В репозитории создай файл `.github/workflows/deploy.yml`:
```yaml
name: demo-pipeline
on: [push]
jobs:
  dev:   { runs-on: ubuntu-latest, steps: [{ run: echo dev-ok }] }
  stage: { runs-on: ubuntu-latest, needs: dev, steps: [{ run: echo stage-ok }] }
  prod:  { runs-on: ubuntu-latest, needs: stage, steps: [{ run: echo prod-ok }] }
```
2. Закоммить, запушь, открой вкладку Actions → последний запуск → сними граф из трёх зелёных боксов.
3. Для GitLab аналогично: `.gitlab-ci.yml` со stages dev/stage/prod → скрин Pipelines.

**Критерий:** три подписанные стадии, всё зелёное.
**План Б:** сними любой зелёный Actions-запуск (даже из одного job) — голосом скажешь «в боевом проекте тут три стадии».

## Ш7. Страница PR → слайд 11

**Что должно быть видно:** заголовок PR, описание, вкладка Files changed (diff красно-зелёный), блок Checks зелёный, кнопка Merge pull request.
**Как сделать:**
1. В `demo-deploy`: новая ветка, маленькое изменение (1–5 строк), push.
```bash
git checkout -b feature/greeting
echo "hello" >> README.md
git add . && git commit -m "feat: greeting" && git push -u origin feature/greeting
```
2. GitHub → Compare & pull request → добавь описание «Что: +приветствие. Проверка: скрин. Риски: нет» → Create pull request.
3. Сними верх страницы (заголовок + описание + Checks), вторым кадром — diff. В презентацию вставь ОДИН кадр (верх с кнопкой Merge), diff покажешь живьём.

**Критерий:** видны заголовок, зелёные Checks и кнопка Merge.
**Важно:** этот же PR используй для Ш8 (не мержь до Ш8!).

## Ш8. Комментарий ревью → слайд 12

**Что должно быть видно:** комментарий ревьюера с предложением кода (suggestion) + кнопка Approve / статус Approved.
**Как сделать:**
1. В PR из Ш7: Files changed → на строке кода нажми `+` → Suggest → предложи улучшение → Add review comment.
2. Переключись на второй аккаунт/вкладку (или попроси друга) либо оставь комментарий сам себе — для учебного скриншота это нормально.
3. Сними комментарий + кнопку «Commit suggestion», вторым кадром — Review changes → Approve.
4. Вставь кадр с suggestion (он нагляднее).

**Критерий:** видно, что ревью — это диалог с кнопками, а не ругань.
**Этика для доклада:** скажи голосом «комментируем код, а не человека» — скрин это подтвердит.

## Ш9. Маркеры конфликта → слайд 13

**Что должно быть видно:** файл с `<<<<<<< HEAD`, `=======`, `>>>>>>> feature/...` + (желательно) кнопка Resolve в GitHub.
**Как сделать (надёжный рецепт конфликта):**
```bash
git checkout main
echo "stroka: MAIN" > conflict.txt && git add . && git commit -m "main version"
git checkout -b feature/conflict
echo "stroka: FEATURE" > conflict.txt && git add . && git commit -m "feature version"
git checkout main
echo "stroka: MAIN v2" > conflict.txt && git add . && git commit -m "main v2"
git merge feature/conflict   # <- будет CONFLICT
code conflict.txt            # открой в редакторе, сними маркеры
git merge --abort            # откатить после скриншота!
```
**Дополнительно:** запушь обе ветки и создай PR — GitHub покажет плашку «This branch has conflicts» + кнопку Resolve conflicts. Сними и её (второй кадр, вставь один).

**Критерий:** маркеры читаются, видно обе версии строки.
**Не забудь:** `git merge --abort` после скриншота, чтобы репозиторий остался чистым для демо!
